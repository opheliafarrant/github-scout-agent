# GitHub Scout Agent 产品需求文档（PRD）V0.2

> 文档状态：S1 产品需求冻结版
>
> 依据：《GitHub Scout Agent 产品需求分析 V0.1》与用户已确认的 D1–D5 五项产品决策。
>
> 本文冻结产品目标、MVP 范围、行为边界和验收要求；不冻结类名、模块结构、框架、部署方式或其他源码实现细节。当前未执行功能测试、真实模型调用或真实 GitHub API 验证。

## 1. 项目背景与产品定位

### 1.1 产品背景

GitHub 项目数量多、命名和文档质量差异大。用户通常知道技术目标，却不一定知道合适的搜索词、Topics、语言筛选或维护状态判断方式。一次搜索请求只能得到候选，不能自动完成证据补充、缺失处理、候选比较和来源报告。

### 1.2 产品定位

GitHub Scout Agent 是一个面向技术需求的、只读的 GitHub 开源项目研究 Agent：

> 用户输入自然语言技术需求，Agent 检索少量公开 GitHub 候选项目，根据工具反馈补充必要证据或调整查询，进行透明比较，并输出包含真实来源链接和不确定性标注的推荐报告。

### 1.3 真实产品价值

产品价值不在于把 GitHub 搜索 API 包一层聊天界面，而在于把以下任务形成可观察闭环：

- 将含糊的自然语言需求转化为检索意图和候选条件。
- 根据第一次工具结果判断是否需要改查、补查或结束。
- 将仓库元数据、README、许可证、语言和维护状态证据放在同一比较上下文中。
- 用确定性规则处理去重、字段缺失、硬性边界和预算控制。
- 将事实、规则计算、模型解释和未知项分开，并提供原始 GitHub 来源。

产品不声称获得 GitHub 未提供的“真实质量分数”，也不把推荐报告当作完整代码质量、安全或生产可用性审计。

### 1.4 产品范围边界

- 只读访问公开 GitHub 信息。
- 不创建、修改、删除 GitHub 仓库，不操作 Issue、PR、Star、账户、设置或权限。
- 不访问私有仓库；MVP 不需要 GitHub 账户管理或写权限。
- 不自动 Clone 仓库，不执行第三方代码，不执行 README 中的命令。
- 不提供任意 Shell 工具或任意 URL 抓取工具。
- 允许在当前项目目录内保存必要的产品文档、日志、测试夹具和报告；不管理项目目录之外的用户文件。

## 2. 目标用户及核心使用场景

### 2.1 首要用户

MVP 首要服务具有明确技术需求、需要比较少量开源候选的开发者、技术负责人、研究人员和学生。开源维护者和 AI Agent 学习者是次要用户。

### 2.2 核心使用场景

| 编号 | 场景 | MVP 价值 | 优先级 |
|---|---|---|---|
| UC-01 | 用户用自然语言描述技术需求并检索候选项目 | 降低 GitHub 搜索表达门槛 | P0 |
| UC-02 | 根据需求筛选少量候选并比较 | 将“找到”转为“有依据地选择” | P0 |
| UC-03 | 补查 README、许可证、语言和维护状态 | 补齐影响采用决策的必要证据 | P0 |
| UC-04 | 第一次结果不足时改写查询或补充检索 | 验证真实 Agent 行为 | P0 |
| UC-05 | 分析用户给定的公开 GitHub 仓库链接 | 支持定向快速评估 | P0 |
| UC-06 | 输出含来源链接、缺失信息和终止原因的报告 | 便于复核、分享和发现风险 | P0 |

### 2.3 明确不承担的场景

MVP 不承担完整代码质量审计、漏洞扫描、供应链审计、依赖许可证传递分析、构建可行性验证、运行性能基准、生产级技术尽调、私有仓库分析或自动化项目管理。

## 3. 五项冻结产品决策

以下决策已经确认，属于本 PRD 的产品基线。后续技术设计不得在没有新事实和用户重新授权的情况下改变它们。

### D1：交互形式为 CLI

- MVP 采用 CLI 命令行交互。
- CLI 必须能够展示任务状态、工具调用、候选结果、错误反馈、继续/终止原因和最终报告。
- 本地 Web UI 留待 MVP 完成后扩展。
- Windows 桌面应用不属于当前 MVP。

### D2：GitHub 认证为两种只读模式

- **无 Token 模式**：可检索和分析公开仓库，受 GitHub 未认证 API 限流约束。
- **用户自配只读 Token 模式**：用户自行提供最小权限只读 Token，用于必要时提高可用额度。
- MVP 不支持私有仓库访问、GitHub 账户管理和任何 GitHub 写操作。
- Token 不得进入模型上下文、最终报告、普通日志或版本控制系统。

### D3：预算机制冻结，具体阈值后定

预算必须由确定性程序强制执行，不能依赖模型自觉遵守。至少包含：

- 最大模型调用轮次；
- 最大 GitHub API 请求次数；
- 任务总执行时间；
- 单次返回内容大小；
- 最大候选项目数量。

具体阈值需要在后续技术验证和测试中根据实际模型、API 响应和资源消耗确定。本 PRD 不伪造精确性能或成本数字。

### D4：MVP 聚焦“少量候选比较与推荐报告”

MVP 的完整目标是：根据自然语言技术需求，检索少量 GitHub 开源候选项目，补充必要证据，进行有依据的比较，并输出可核验的推荐报告。

必需行为包括自然语言输入、公开仓库检索、少量候选筛选、元数据查询、必要的 README/许可证/语言/维护状态分析、反馈驱动的补查/改查/终止、真实来源比较、缺失和不确定性标注。

### D5：先验收一个支持 Tool Calling 的 OpenAI-compatible 端点

- 模型配置至少包括 Base URL、API Key 和 Model。
- MVP 先使用一个经过实际验证支持 Tool Calling 的 OpenAI-compatible API 端点完成验收。
- 保留后续更换兼容端点的能力，但不提前建设复杂的多 Provider 框架。
- 不支持 Tool Calling 的模型必须明确提示不满足运行要求，不自动解析非结构化文本命令作为替代。

## 4. MVP 功能范围与优先级

### 4.1 P0 必须具备

| 功能编号 | 功能 | 产品要求 |
|---|---|---|
| FR-01 | 自然语言输入 | 接收技术需求；可识别目标、约束、期望候选规模和报告目的；不明确时有限澄清或明确标注默认值 |
| FR-02 | 公开仓库搜索 | 使用 GitHub 官方公开数据接口检索候选，记录查询、排序、分页和返回状态 |
| FR-03 | 指定仓库分析 | 接收并验证公开 GitHub 仓库地址，读取该仓库可用证据 |
| FR-04 | 候选证据补充 | 按需补充仓库元数据、README、许可证、语言、Topics、归档和维护相关字段 |
| FR-05 | Agent Loop | 执行“理解需求—选择工具—获取数据—读取反馈—继续/改查/补查/终止—报告”闭环 |
| FR-06 | 反馈驱动分支 | 结果不足、证据缺失、仓库归档、结果不完整或错误状态必须能触发不同下一步 |
| FR-07 | 透明比较与排序 | 使用可解释维度和确定性规则辅助排序；Stars/Forks 只能作为信号，不能直接代表质量 |
| FR-08 | 来源报告 | 输出候选、比较、推荐依据、缺失信息、抓取时间、查询信息、原始 GitHub 链接和任务终止状态 |
| FR-09 | CLI 可观测性 | 显示当前阶段、工具名称、状态、返回数量、继续原因、错误分类、预算状态和结束原因 |
| FR-10 | 只读安全边界 | 只允许公开 GitHub 只读能力；不开放写操作、Clone、代码执行、任意 Shell 或任意 URL |
| FR-11 | 预算强制控制 | 程序强制执行 D3 的五类预算；达到上限安全停止并说明已完成内容 |
| FR-12 | 缺失与失败处理 | 区分空结果、字段缺失、README 不存在、许可证未识别、网络失败、限流、权限错误和模型工具调用错误 |

### 4.2 P1 后续版本

- 本地 Web UI：在 CLI 闭环稳定后展示任务时间线、候选表和报告。
- 更丰富的查询策略和多轮补查。
- 经验证的更多 OpenAI-compatible Tool Calling 端点。
- 历史报告、用户偏好和可选本地索引。

### 4.3 P2 或明确排除

以下不属于 MVP：GraphQL 迁移、长期记忆、RAG 向量库、多 Agent 协作、复杂数据库、云端多用户服务、Windows 桌面应用、自动订阅监控、私有仓库、GitHub 写操作、Clone、构建、依赖安装、代码执行、漏洞/供应链审计和生产级技术尽调。

## 5. Agent 核心能力及行为边界

### 5.1 必须存在的闭环

MVP 必须实现并可通过测试观察到以下序列：

```text
自然语言理解
  → 选择只读工具
  → 获取 GitHub 数据
  → 接收并解释工具反馈
  → 选择补查、改查、继续、终止或生成报告
  → 生成带来源的报告
```

固定执行“搜索—排序—报告”三步不算满足本需求。至少需要覆盖以下可分辨分支：

| 工具结果 | Agent 可选择的下一步 | 必须保留的事实 |
|---|---|---|
| 结果过少或为空 | 在预算内改写查询、扩大范围，或说明无法继续 | 原查询、结果数量、调整/终止原因 |
| 候选缺少必要证据 | 补查 README、许可证、语言或元数据，或标记未知 | 缺失字段和补查结果 |
| 仓库已归档 | 保留候选但在比较和推荐中反映风险，或按需求排除 | `archived=true` 原始状态 |
| 搜索结果不完整 | 标记不完整，必要时调整查询或停止 | `incomplete_results` 和查询范围 |
| API 限流、超时或连续失败 | 按程序策略退避、重试或安全结束 | 状态码、错误分类、终止原因 |
| 达到预算 | 立即停止新的模型/API调用，输出部分结果和限制说明 | 达到的预算类型及已完成工作 |

### 5.2 Agent 与确定性程序的分工

| 能力 | 主体 | 产品边界 |
|---|---|---|
| 需求意图理解、查询候选词选择 | Agent | 只能提出受约束的结构化行动 |
| 下一步补查、改查或结束判断 | Agent + 程序预算 | Agent 不能突破硬性预算 |
| API 请求、主机校验、超时、退避和重试 | 确定性程序 | 模型不能直接发任意网络请求 |
| 响应解析、去重、字段归一化、URL 校验 | 确定性程序 | 不交给模型自由改写事实 |
| 评分计算和硬性过滤 | 确定性程序 | 规则可复现、可测试、可解释 |
| 推荐解释和报告措辞 | Agent 基于结构化证据 | 不得新增工具结果中不存在的事实 |
| 日志、权限、预算和终止 | 确定性程序 | 不依赖提示词服从 |

不要求展示模型隐藏思维链。CLI 展示行动事件、工具结果摘要、下一步原因和最终证据即可。

## 6. GitHub 数据来源、真实性和引用要求

### 6.1 数据来源基线

MVP 优先使用 GitHub 官方 REST API。官方文档说明，搜索端点支持查询语法、分页和排序；仓库详情、README/Contents、语言、Topics 和许可证有对应只读接口。公开资源在相应端点可不认证读取，认证方式和细粒度 Token 权限应按实施时的官方文档核验。

- [REST API endpoints for search](https://docs.github.com/en/rest/search/search?apiVersion=2022-11-28)
- [REST API endpoints for repositories](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28)
- [REST API endpoints for repository contents](https://docs.github.com/en/rest/repos/contents?apiVersion=2022-11-28)
- [REST API endpoints for licenses](https://docs.github.com/en/rest/licenses/licenses?apiVersion=2022-11-28)

GraphQL 暂不进入 MVP。其字段选择灵活，但有点数、节点数和超时限制；是否采用必须等 REST MVP 的真实请求模式和性能证据出现后重新评估。

- [About the GraphQL API](https://docs.github.com/en/graphql/overview/about-the-graphql-api)
- [Rate limits and query limits for the GraphQL API](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)

### 6.2 字段语义和局限

| 字段/内容 | 可用于 | 不得推导为 |
|---|---|---|
| `full_name`、`html_url`、描述 | 身份确认和来源链接 | 模型生成的项目事实 |
| `stargazers_count`、`forks_count` | 社区采用信号 | 质量、维护性、安全性或生产适用性证明 |
| `created_at`、`updated_at`、`pushed_at` | 时间线和维护相关线索 | “活跃”这一无条件结论 |
| `archived`、`disabled`、`fork` | 状态警示和过滤 | 未归档即适合使用 |
| `license` / SPDX 字段 | GitHub 识别到的许可证信息 | 法律审查或依赖许可证结论 |
| Topics | 查询扩展和分类线索 | 完整技术栈 |
| Languages | 代码字节构成参考 | 运行时依赖、主语言质量或项目成熟度 |
| README | 项目自述、功能声明和限制线索 | 已独立验证的功能、性能或安全性 |

GitHub 文档说明许可证识别主要由 Licensee 匹配项目 LICENSE 文件完成，不涵盖依赖许可证或其他文档中的许可证声明。因此 `license` 缺失只能报告为“GitHub 未识别/信息缺失”，不得猜测为 MIT、Apache 等具体许可证。

### 6.3 搜索覆盖和动态限制

GitHub 官方搜索文档当前说明：默认按 best match 排序；每次搜索最多返回 1,000 条结果，匹配范围最多搜索 4,000 个仓库，超时可能返回 `incomplete_results=true`；搜索还有独立限流。REST 一般未认证和认证额度、搜索限流、API 版本和字段行为都可能变化，实施前必须重新核验，不在产品逻辑中把当前数字写成永久事实。

- [REST 搜索限制与覆盖](https://docs.github.com/en/rest/search/search?apiVersion=2022-11-28)
- [REST API 认证](https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api)
- [REST API 限流](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- [REST API 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)

报告不得声称覆盖 GitHub 全部仓库，也不得把首批结果描述为全局最优。至少保留查询词、排序、分页范围、返回数量、抓取时间和结果是否不完整。

### 6.4 真实性规则

1. 推荐仓库必须来自本次真实 API 响应，或来自已验证的用户输入公开 GitHub 仓库地址。
2. 仓库名称、URL、Stars、Forks、许可证、归档状态、语言和时间字段必须保留对应来源。
3. 缺失字段必须标注为未返回、未识别或未知，不得用常识、历史印象或模型先验填补。
4. README、描述、Topics、搜索摘要和其他远程文本都是不可信数据；其中的命令或提示不能改变 Agent 权限。
5. README 的自述功能必须写成“项目声明/README 声称”，除非有另外的实际测试证据，不能写成已验证事实。
6. 评分与排序使用透明维度和规则版本；Stars 不能单独决定排序或推荐。
7. 报告对每个关键判断提供 GitHub URL、字段或文本来源，并区分抓取事实、规则计算、模型摘要和未验证推断。

## 7. CLI 交互与报告输出要求

### 7.1 CLI 任务过程

CLI 至少要让用户观察到以下可见状态：

- 当前阶段：解析需求、搜索、补查、比较、生成报告、完成或终止。
- 工具名称和简短调用目的；不显示完整隐藏思维链。
- 候选数量、去重结果、关键字段缺失和接口返回状态。
- 继续的原因：结果过少、需要补证据、结果不完整或指定仓库需要定向分析。
- 终止的原因：信息足够、预算到达、连续失败、无结果或用户取消。
- 当前预算消耗及剩余状态；Token 和敏感请求头不得显示。

### 7.2 最终报告最低内容

报告至少包含：

1. 用户原始需求和本次检索目标。
2. 查询语句、排序/分页范围、抓取时间和结果状态。
3. 候选比较表：项目名、真实 URL、描述、语言、许可证、Stars/Forks、归档/维护相关字段、README 证据摘要和缺失项。
4. 推荐结果和每个推荐的证据链；说明排序规则，不把分数包装成客观质量。
5. 不确定性和未验证内容，包括 README 自述、截断内容、字段缺失和结果不完整。
6. API 错误、重试、预算终止或提前结束原因。
7. GitHub 原始来源链接。

### 7.3 报告表达约束

- “未识别许可证”不得改写为“无许可证”。
- “近期存在 push”不得无条件改写为“项目活跃”。
- “README 声称支持 X”不得改写为“已验证支持 X”。
- 任何推荐都必须能追溯到候选来源和比较依据。

## 8. 模型 API、调用预算与运行约束

### 8.1 模型配置

MVP 支持用户配置：

- `Base URL`
- `API Key`
- `Model`

还需要可观测地处理请求超时、输出长度、Tool Calling 能力、响应格式异常和服务端错误。OpenAI-compatible 不代表行为完全一致；工具定义格式、工具调用返回结构、流式响应、错误格式、schema 遵循度、上下文窗口和重试语义必须在后续实际验证中确认。

### 8.2 Tool Calling 兼容策略

- MVP 只验收一个实际验证支持 Tool Calling 的端点。
- 模型不支持 Tool Calling 时，CLI 必须明确提示配置不满足，不进入伪工具协议。
- 不允许把模型输出的任意文本当成 URL、Shell 命令、HTTP 方法或权限变更指令。
- 后续更换端点时必须重新验证工具调用、错误处理、预算和真实性验收，不以“兼容 OpenAI”标签作为充分证据。

### 8.3 五类预算

预算控制是产品必需能力，具体阈值暂不冻结：

| 预算 | 控制对象 | 超限行为 |
|---|---|---|
| 模型调用轮次 | Agent Loop 的模型请求次数 | 停止新的模型调用，输出部分结果和原因 |
| GitHub API 请求次数 | 搜索和证据获取请求总数 | 停止新的 GitHub 请求，报告已完成证据 |
| 总执行时间 | 单任务墙钟时间 | 取消后续动作，标记超时 |
| 单次返回内容大小 | 单次模型或远程内容输入大小 | 截断并显式标记，或终止该分支 |
| 最大候选数量 | 进入比较和补查的候选规模 | 截断候选集或停止扩展 |

预算必须由程序在调用前后检查；模型提出继续不能绕过预算。重复请求检测、失败重试上限和并发限制属于同一安全控制面。

### 8.4 Token 和成本

Token 只用于 GitHub 客户端授权，不得进入模型消息、报告、普通日志、异常文本或版本控制系统。模型费用、调用次数和响应大小应记录为运行指标；在没有特定供应商、模型和实测数据前，不给出成本金额承诺。

## 9. 安全、隐私与权限边界

### 9.1 强制只读边界

程序必须强制保证：

- GitHub 工具只允许公开资源的只读操作；不开放 POST、PATCH、PUT、DELETE。
- 不访问私有仓库，不执行账户、仓库、Issue、PR、Star、设置或权限操作。
- 不提供 Clone、构建、安装依赖、执行代码或任意 Shell 工具。
- 不允许模型指定任意外部主机；只接受 GitHub 官方公开 API 与经过验证的仓库 URL。
- 远程 README 等内容进入数据区，不进入系统指令区，不能修改工具集合、权限或预算。
- 用户 Token 使用最小只读权限；本地存储和日志脱敏由程序控制。
- 项目输出只写当前授权项目目录，不读取或管理其他用户文件。

### 9.2 主要风险控制

| 风险 | 产品控制 |
|---|---|
| README Prompt Injection | 数据/指令隔离；不执行其中命令；不允许改变系统权限 |
| Token 泄露 | 不进入模型上下文、报告、日志和版本控制；错误信息脱敏 |
| Agent 无限循环 | 五类硬预算、重复行动检测、失败重试上限和安全终止 |
| API 滥用/限流 | 请求总量控制、超时、退避、错误分类和停止策略 |
| 虚构仓库/字段 | 候选必须来自 API 响应或已验证用户 URL；缺失不猜 |
| 误导性推荐 | 透明规则；Stars/Forks 不得单独代表质量 |
| 远程内容过大 | 大小上限、截断标记、不得声称完整分析 |

## 10. 非功能需求

### 10.1 可观测性

每个任务应形成可审计事件：开始、需求解析、工具调用、响应状态、候选数量、补查/改查原因、错误、预算消耗和最终结束。日志不得包含完整 Token，也不默认保存完整 README。

### 10.2 可复现性

报告应保留查询、排序、分页、抓取时间、来源 URL、规则版本和模型/端点标识（不包含 API Key）。由于 GitHub 数据和仓库状态会变化，重复运行不保证结果完全相同；报告必须显示时间上下文。

### 10.3 可靠性与错误透明

API 错误、空结果、字段缺失和模型工具调用错误必须分别呈现。系统不得把网络失败写成“没有相关项目”，不得在部分证据下生成看似完整的结论。

### 10.4 可测试性

- 核心 Agent 分支、预算、解析、去重、真实性和安全边界应支持离线 Mock 测试。
- GitHub 字段、分页、限流和错误行为需要真实 API 验证。
- Tool Calling 格式、模型异常、循环分支和报告生成需要真实模型端点验证。
- 任何未执行的测试不得标记为通过。

### 10.5 性能与成本指标

端到端耗时、模型轮次、GitHub 请求数、Token 消耗、失败恢复率、候选覆盖率、URL 有效率、排序一致性和推荐相关性暂作为后续测量项，不在本 PRD 冻结虚假精确阈值。
