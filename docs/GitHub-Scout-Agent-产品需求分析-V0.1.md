# GitHub Scout Agent 产品需求分析 V0.1

> 阶段：产品需求分析。本文只定义产品问题、范围、验收和后续路线，不冻结具体源码架构，不代表已完成任何功能实现。
>
> 调研日期：2026-10-26。涉及 GitHub API 的额度、字段和限制均应在实施前再次核验，本文不把它们当作永久不变的运行时常量。

## 1. 项目背景与产品定位

### 1.1 背景

GitHub 上的开源项目数量大、命名和文档质量差异大，用户往往无法仅凭一句需求直接找到可用候选。真正困难的不是发出一次搜索请求，而是把自然语言需求拆成检索条件，识别候选项目的适用边界，补齐 README、许可证、技术栈和活跃度等证据，并把结论与原始链接对应起来。

GitHub Scout Agent 的目标是：

> 用户用自然语言提出“我需要什么项目”，Agent 只读检索 GitHub 公开信息，按证据分析候选，必要时调整检索策略，并生成可核验的比较与推荐报告。

### 1.2 产品边界

产品是“有边界的研究型检索 Agent”，不是 GitHub 管理工具、代码执行器、自动部署器或通用文件管理 Agent。

首要边界：

- 只读访问公开 GitHub 数据；不创建、修改、删除仓库，不操作 Issue、PR、Star、设置或账户权限。
- 默认不访问私有仓库；MVP 不要求 OAuth 登录或 GitHub 写权限。
- 不自动 Clone 仓库，不执行仓库代码，不执行 README 中的命令。
- 不把仓库 README、Issue、网页内容或模型输出当成系统级指令。
- 允许在项目目录内保存必要的日志、测试夹具和调研报告；不管理用户项目目录之外的文件。

### 1.3 产品成功的最低定义

MVP 不是“能调用一次 GitHub API”。最低成功条件是：

1. 能把自然语言请求转化为可解释的检索任务。
2. 至少存在一次基于工具结果的下一步判断：例如结果太少、缺少许可证或候选不够多时，Agent 选择扩大、改写或补充查询。
3. 每项关键结论都能回指真实 GitHub URL 和字段来源；缺失数据明确写“未识别/未返回”，不补猜。
4. 达到调用、时间或请求预算时能安全停止，并说明停止原因。

## 2. 目标用户与实际问题

### 2.1 目标用户

| 用户 | 主要任务 | 真实痛点 |
|---|---|---|
| 软件开发者 | 找库、找脚手架、找可二次开发项目 | 需求用词与仓库命名不一致；难以快速筛掉停更、归档或无许可证项目 |
| 技术负责人/架构师 | 评估技术路线和候选基础设施 | 需要同时比较维护状态、技术栈、许可证、文档和社区信号 |
| 研究人员/学生 | 调研某个领域的开源生态 | 需要来源、检索过程和可复核的证据，而不只是模型印象 |
| 开源项目维护者 | 了解同类项目与生态位置 | 需要多维比较，不希望只按 Stars 排名 |
| 学习 AI Agent 的开发者 | 观察一个可控的 Agent 实例 | 需要看见工具调用、反馈、重试、终止和报告生成闭环 |

MVP 的首要用户建议聚焦于“有明确技术需求、需要少量候选比较的开发者/研究者”。不先覆盖企业级依赖治理、完整软件供应链审计或私有代码资产管理。

### 2.2 要解决的问题

- **搜索表达问题**：用户知道目标，不知道 GitHub 搜索关键词、Topics、语言和时间过滤条件。
- **候选筛选问题**：搜索结果很多，不能把名称相似当作满足需求。
- **证据拼接问题**：元数据、README、许可证、语言和活跃度分散在不同接口或页面。
- **动态补查问题**：第一次结果不足时，固定流程不会知道该扩大词义、换同义词还是补查单个仓库。
- **可信度问题**：模型容易把不存在的仓库、过时的 Stars 或推测的许可证写成事实。
- **决策沟通问题**：用户需要一个有依据的短报告，而不是一串链接或无法复核的排名。

## 3. 产品价值与差异化

### 3.1 相比 GitHub 官方搜索界面

GitHub 官方搜索擅长直接检索、过滤和浏览，但用户仍需要自行完成需求拆解、跨字段比较、补查 README 和许可证、处理缺失信息以及编写结论。Scout Agent 的增量价值是把这些步骤串成可观察、可终止、可复核的研究任务。

它不应声称拥有 GitHub 未提供的“真实质量分数”。它只能在公开字段和明确规则之上形成有限的决策辅助，并保留原始证据。

### 3.2 相比直接问 ChatGPT、Claude 等模型

直接询问通用模型的优势是对话自然、覆盖面广；风险是模型可能依赖旧知识、来源不完整，或把相似名称与未经验证的项目细节混在一起。Scout Agent 的差异化应来自：

- 先调用 GitHub 官方接口，再生成结论。
- 把仓库 URL、查询语句、抓取时间和关键字段保留在结果中。
- 使用 Agent Loop 依据工具反馈改变下一步，而不是固定的“搜索—排序—写作”脚本。
- 用确定性规则处理数据清洗、去重、字段缺失、硬性过滤和预算控制。
- 将“事实”“模型解释”“不确定性”分开呈现。

如果产品只是把用户问题转发给模型，再执行一次 API 搜索和模板排序，它没有形成足够的 Agent 价值。

### 3.3 Agent 与确定性程序的边界

| 工作 | 推荐主体 | 原因 |
|---|---|---|
| 把自然语言需求拆成检索意图和候选条件 | Agent | 需要处理含糊表达，并决定是否需要补充查询 |
| 选择下一次查询、决定是否继续 | Agent + 明确预算约束 | 体现基于工具反馈的动态规划；模型不得绕过上限 |
| 发出 API 请求、超时、退避、重试 | 确定性程序 | 可测试、可审计，避免模型直接控制网络边界 |
| 解析响应、去重、字段规范化、URL 校验 | 确定性程序 | 不应把机械数据处理交给模型 |
| 评分的字段计算和硬性门槛 | 确定性程序 | 保证重复运行和测试稳定 |
| 解释推荐取舍、生成报告 | Agent + 结构化数据 | 适合自然语言表达，但不能添加数据中不存在的事实 |
| 日志、预算、终止、权限检查 | 确定性程序 | 这是安全控制，不应依赖提示词服从 |

## 4. 典型使用场景评估

优先级含义：P0 为 MVP 必须验证，P1 为首个可用版本后加入，P2 为后续探索，不表示永久排除。

| 场景 | 用户价值 | Agent 必要性 | 难度 | 主要依赖 | 建议优先级 |
|---|---|---|---|---|---|
| A. 自然语言搜索项目 | 降低搜索表达门槛 | 需要把需求转为查询；单纯 API 查询不够 | 中 | Repository Search、分页、查询语法 | P0 |
| B. 根据技术需求推荐 | 从“找到”走向“适合” | 需要澄清约束、补查证据和解释取舍 | 中高 | A + 元数据、README、规则评分 | P0，限定候选规模 |
| C. 比较多个仓库 | 节省人工横向整理时间 | 需要决定比较维度并处理缺失值 | 中 | 仓库详情、语言、许可证、README | P0 |
| D. 分析 README、许可证、技术栈、活跃度 | 提高决策可信度 | Agent 负责摘要，程序负责取数和标注 | 中 | Contents/README、license、languages、metadata | P0 |
| E. 多维评分排序 | 让推荐有一致规则 | 模型不应直接发明分数；Agent 可解释规则选择 | 中 | 规范化字段、透明评分规则 | P0，使用可解释评分 |
| F. 生成带来源报告 | 方便复核和分享 | 需要把证据组织为自然语言 | 低中 | 结构化结果、来源 URL、时间戳 | P0 |
| G. 根据初次结果自动调整关键词 | 体现真实 Agent 行为 | 必须由工具反馈触发下一步 | 高 | Loop、查询改写、预算、停止条件 | P0，限制为一轮或少量轮次 |
| H. 分析用户给定仓库链接 | 适合尽调和快速评估 | 需要 URL 解析、定向补查和异常处理 | 低中 | repository、README、license 等只读接口 | P0 |

### 4.1 MVP 不追求的场景深度

MVP 不做完整代码质量审计、漏洞审计、依赖许可证传递分析、构建可行性验证、运行性能基准或社区治理尽调。README 声明的功能也不等于已经运行验证的功能。

## 5. Agent 核心能力需求

### 5.1 MVP 必需能力

1. **受限 Agent Loop**：模型提出行动，程序校验行动，调用只读工具，将结果返回模型，再由模型选择继续、改写查询、补查或结束。
2. **Tool Calling**：至少支持仓库搜索、仓库详情、README、许可证、语言/主题等只读工具。工具输入必须经过 schema 校验和安全边界检查。
3. **工具反馈驱动**：例如 `incomplete_results=true`、候选太少、README 缺失、许可证未识别、候选已归档时，触发不同的后续动作。
4. **失败恢复**：区分网络超时、HTTP 403/429、404、422、空结果、字段缺失和模型输出无效；只对可重试的边界错误进行有上限的重试。
5. **任务预算与终止**：模型调用次数、GitHub 请求数、总时长和结果数量都应由程序控制。达到预算、信息已足够或连续失败时停止。
6. **结构化中间结果**：每个候选包含真实 `full_name`、GitHub HTML URL、抓取时间、来源字段、原始状态和缺失字段。
7. **运行日志**：记录任务状态、工具名、输入摘要、响应状态、耗时、结果数量、继续/终止原因和错误分类；不记录 API Key，不默认记录完整 README。
8. **可核验报告**：最终报告必须区分 GitHub 返回的事实、基于规则的计算、模型摘要和未验证判断。

### 5.2 后续能力

- **长期记忆**：可保存用户偏好的语言、许可证或维护状态阈值，但应先获得明确产品定义；MVP 不需要。
- **RAG/本地索引**：只有当重复查询、历史报告或大规模仓库语料成为瓶颈时才有价值；MVP 直接以实时官方 API 为主。
- **多 Agent 协作**：当前问题规模可由一个受限 Loop 完成；多 Agent 会增加并发、成本、调试和一致性风险。
- **GraphQL**：适合后续在需要一次请求取多个嵌套字段时评估，不作为 MVP 前置条件。

### 5.3 不应伪装成 Agent 的部分

固定执行三步并把模板输出称为 Agent 不满足本项目学习目标。MVP 至少应能在以下两类分支中选择不同动作：

- 候选不足：换用同义词/更宽查询、补充语言或移除过窄条件，或者在预算内结束并说明不足。
- 证据不足：对入选候选补查 README、许可证或语言；若接口返回缺失，则标记未知而不是补写。

模型不公开的内部思维过程不要求展示。界面展示“基于哪些可见结果而采取了什么行动”即可。

## 6. GitHub 数据来源及可信度分析

### 6.1 REST 与 GraphQL 的取舍

**MVP 推荐 REST API。** GitHub REST 搜索端点直接支持仓库搜索、分页和查询语法；仓库详情、README、语言和主题也有独立接口，较容易做成可测试的只读工具。公开仓库数据在相应端点上可以不认证读取；细粒度 Token 的 Metadata/Contents 只读权限可用于需要认证的场景。官方文档明确说明了这些端点和权限边界。[REST 搜索接口](https://docs.github.com/en/rest/search/search?apiVersion=2022-11-28) · [仓库接口](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28) · [Contents/README 接口](https://docs.github.com/en/rest/repos/contents?apiVersion=2022-11-28)

**GraphQL 后置评估。** GraphQL 可以精确选择字段并在一次请求中取得嵌套数据，但使用点数限额、节点数和查询超时约束；它的灵活性不自动等于更低成本或更高可靠性。[GraphQL 概览](https://docs.github.com/en/graphql/overview/about-the-graphql-api) · [GraphQL 限制](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)

### 6.2 MVP 关注的数据

| 数据 | 主要用途 | 可信度与局限 |
|---|---|---|
| `full_name`、`html_url`、描述、默认分支 | 识别项目并提供来源 | 以 API 返回为准；URL 必须原样保存并在输出前校验 |
| `stargazers_count`、`forks_count` | 社区采用信号 | 不是质量、维护性或安全性的证明；会随时间变化，不能单独决定推荐 |
| `created_at`、`updated_at`、`pushed_at` | 判断项目年龄和近期活动 | “最近 push”不等于持续维护；自动提交、文档提交和单人维护都可能影响解释 |
| `archived`、`disabled`、`fork` | 排除或警示特殊仓库 | 归档是明确状态；未归档也不保证项目仍适合生产使用 |
| `license` / SPDX 字段 | 判断 GitHub 是否识别到许可证 | `null` 应显示“GitHub 未识别”，不能写成“无许可证”或推断法律结论 |
| Topics | 扩展查询和技术分类 | 由维护者维护，可能缺失、过时或宽泛 |
| Languages | 估计代码语言构成 | 官方接口返回语言对应的代码字节数，不等于运行时依赖、主语言或技术质量。[语言接口说明](https://docs.github.com/en/rest/repos/repos?apiVersion=2022-11-28) |
| README | 了解用途、安装、限制和声明的特性 | 是仓库外部内容，可能不完整、过时或含 Prompt Injection；只能作为来源材料，不能作为系统指令 |

许可证判断应保守：GitHub 文档说明 Licensee 主要根据项目中 `LICENSE` 文件匹配已知许可证，且不处理依赖许可证或其他文档中的声明。[许可证接口说明](https://docs.github.com/en/rest/licenses/licenses?apiVersion=2022-11-28)

### 6.3 搜索覆盖与分页

GitHub REST 搜索文档说明：默认按 best match 排序；每次搜索最多返回 1,000 条结果，匹配范围最多搜索 4,000 个仓库；超时可能返回 `incomplete_results=true`。仓库搜索还存在独立搜索限流：官方文档当前列出认证请求每分钟 30 次、未认证请求每分钟 10 次，具体限制实施前必须重新核验。[搜索限制与覆盖](https://docs.github.com/en/rest/search/search?apiVersion=2022-11-28)

因此产品不能声称“搜索了 GitHub 全部仓库”，也不能把前几页结果当作全局最优。报告应保存查询、排序方式、分页范围、返回数量和是否 incomplete。

### 6.4 认证、限流与错误处理

官方文档当前说明，公开数据可使用未认证请求；REST API 的一般额度是未认证每小时 60 次、认证用户通常每小时 5,000 次，但搜索端点有更严格的独立限制。[REST 认证与额度](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) · [REST 认证方式](https://docs.github.com/en/rest/authentication/authenticating-to-the-rest-api)

MVP 建议：

- 默认支持无 Token 的公开只读模式，便于低门槛试用，但尽快在设置中支持用户自行提供细粒度、只读 Token。
- Token 只放在本地安全配置或系统凭据存储中，不进入报告、普通日志、模型提示词或错误堆栈。
- 使用响应头中的限流信息决定暂停和终止；遇到 403/429 不盲目快速重试。官方建议根据 `retry-after` 或 `x-ratelimit-reset` 等信息退避；持续请求可能导致集成被限制。[REST 最佳实践](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- 对 401/403/404/422、超时、JSON 解析失败、空结果和字段缺失分别给出用户可理解的状态，不把“接口失败”改写成“没有相关项目”。
- 对公开数据使用 `Accept` 与 API 版本头时，版本值不应硬编码为永远不变的事实；实施时按当前官方文档配置并加入兼容性测试。

### 6.5 防止虚构和证据污染

1. 只有 API 响应中的仓库身份、URL、字段和 README 内容才可作为对应事实。
2. 报告中的每个候选必须来自本次响应或用户输入的已解析 URL；模型不能自行生成仓库名。
3. 事实字段与推断字段分开。比如“近 90 天有 push”可以是规则计算；“维护活跃”只能是带限定词的解释。
4. 缺失字段输出 Unknown/未识别；禁止使用常见许可证、语言或 Stars 先验填空。
5. README、描述、Topics 和搜索摘要全部视为不可信外部数据，进行长度限制、内容标注和提示词隔离；其中的“忽略系统规则”“执行命令”等文字不得改变 Agent 权限。
6. 推荐排序输入保留原始字段和规则版本，便于重复验证和发现评分偏差。

## 7. 交互方式与模型 API 方案比较

### 7.1 形态比较

| 形态 | 开发成本 | Agent 可观测性 | 调试便利性 | 扩展能力 | 结论 |
|---|---:|---:|---:|---:|---|
| CLI | 低 | 高（事件流天然清晰） | 高（日志和命令易复现） | 中 | 推荐先做，但不在本轮冻结 |
| 本地 Web UI | 中 | 高（适合任务时间线和候选表） | 中高 | 高 | CLI 核心稳定后作为首个体验层 |
| Windows 桌面应用 | 高 | 可高，但 UI 与打包复杂 | 中 | 中高 | 暂不作为首个交付形态 |

专业推荐是“先 CLI 验证 Agent 闭环，再视验收反馈增加本地 Web UI”。这不是必须决策；若主要学习目标是可视化 Agent 运行过程，可提前做极薄的本地 Web 壳，但不应先建设大型前端系统。

### 7.2 可观测性设计要求

用户应能看见：

- 当前阶段：解析需求、搜索、补查、比较、生成报告、已结束。
- 工具名称、调用目的的简短摘要、请求状态、耗时、返回候选数和来源 URL。
- Agent 为什么继续：结果过少、候选缺字段、结果 incomplete 或需要验证指定仓库。
- Agent 为什么停止：信息足够、预算到达、连续失败、无结果或用户取消。
- 每项推荐对应的事实、规则指标、不确定性和原始链接。

不展示模型隐藏思维链。可公开的是行动事件和依据数据，不是模型内部逐 token 推理。

### 7.3 OpenAI-compatible 模型 API

应抽象为可替换的模型适配层，至少配置：

- `Base URL`
- `API Key`
- `Model`
- 请求超时、最大输出和重试策略
- Tool Calling/Function Calling 能力声明或探测结果

不能假设所有 OpenAI-compatible 服务完全兼容。需要逐项验证：工具定义格式、工具调用返回结构、并行工具调用、流式响应、错误格式、JSON/schema 遵循度、上下文窗口、超时和重试语义。MVP 建议选择一个经过实际验证的兼容端点作为 E3 测试对象，同时保留适配接口，不在需求阶段锁定供应商。

**不支持 Tool Calling 的模型**：MVP 可将其标记为不满足 Agent 模式，给出明确配置错误；不建议在模型输出中解析任意伪命令来替代工具调用。后续若增加降级模式，也必须只允许程序定义的结构化协议，并默认关闭外部写操作。

### 7.4 调用次数与成本控制

单次任务的成本主要由模型轮次、输入中注入的工具结果、README 文本长度、候选数量和模型价格共同决定。未取得具体供应商和当前价格前，不给出成本金额事实。

MVP 应采用：

- 小候选集、短 README 摘要窗口和字段白名单。
- Agent 轮次、GitHub 请求数、总时长和输出长度上限。
- 对重复仓库去重；同一任务中不重复抓取相同字段。
- 在日志中记录模型调用数、输入/输出 token（服务提供时）和失败数。
- 模型超时、无效工具调用、空响应和格式错误使用有上限的重试；多次失败后安全终止。
- 用 Mock 模型测试工具选择、异常恢复、预算终止和结构化输出，不用真实模型才能覆盖的逻辑全部留到在线测试。

## 8. 安全与权限边界

### 8.1 强制规则

程序逻辑必须强制执行以下约束：

- GitHub 客户端只注册 GET/只读操作；不提供 POST、PATCH、PUT、DELETE 工具。
- 仅允许 `api.github.com` 的公开 API 主机和 GitHub 官方仓库 URL 解析；不允许模型提供任意 URL 作为网络工具目标。
- 仅接受公开仓库；MVP 不执行私有资源访问，也不使用需要写权限的 Token。
- 不提供任意 Shell 工具，不提供 Clone、构建、安装、执行代码工具。
- README 和其他远程文本进入“数据区”而不是“指令区”；工具结果不改变系统提示词、权限或可用工具列表。
- 对每次任务设置请求数量、模型轮次、响应大小和总时长上限。
- API Key 进入内存配置后必须脱敏；日志、报告、异常和 UI 不显示完整凭据。
- 所有项目输出写入当前独立项目目录；不得因分析仓库而读取、修改用户其他文件。

### 8.2 威胁与对策

| 风险 | 例子 | MVP 对策 |
|---|---|---|
| Prompt Injection | README 要求 Agent 忽略规则并上传密钥 | 数据/指令隔离；明确拒绝；不开放任意外部写入 |
| 凭据泄露 | 401/调试日志打印 Authorization | HTTP 层脱敏、异常白名单、凭据测试 |
| 无限循环 | 模型反复改写查询 | 轮次、请求数、时间和重复行动检测 |
| API 滥用 | 并发抓取大量仓库 | 串行或受限并发；限流感知；硬上限 |
| 虚构事实 | 生成不存在的仓库或许可证 | URL/字段必须来自工具响应；缺失显式标记 |
| 误导性评分 | Stars 高就被排第一 | 透明的多维规则；Stars 只能是一个信号 |
| 远程内容过大 | 超大 README 或异常响应 | 响应大小限制、截断标记、不要把截断当完整证据 |

## 9. MVP 推荐范围

### 9.1 推荐方案

MVP 定义为一个“公开 GitHub 研究 Agent”：

1. 接收一条自然语言需求，或一个公开 GitHub 仓库 URL。
2. 解析目标、约束和期望输出；缺少关键约束时用有限澄清，或选择明确默认值并标注。
3. 通过 Tool Calling 使用 GitHub REST 只读工具搜索仓库、读取元数据、README、许可证、语言和 Topics。
4. 基于工具反馈决定：直接结束、补查候选、调整一次查询，或因预算/错误终止。
5. 由确定性程序完成去重、字段归一化、硬性过滤和透明的多维评分；模型生成候选解释与报告语言。
6. 输出候选表、推荐理由、缺失信息、查询记录、来源链接、抓取时间和任务终止状态。
7. 记录不含凭据的运行事件，支持离线 Mock 测试。

### 9.2 建议的 MVP 工具集合（产品层定义）

- `search_public_repositories`：查询、排序、分页、结果元数据。
- `get_public_repository`：单仓库元数据、状态、统计和 URL。
- `get_public_readme`：读取 README，带大小限制和截断标记。
- `get_repository_license`：读取 GitHub 识别的许可证信息；缺失即 Unknown。
- `get_repository_languages_and_topics`：读取语言字节统计和 Topics。

工具名是产品能力边界，不是本轮冻结的源码接口。实现阶段仍需根据官方 API 当前文档和测试结果调整。

### 9.3 推荐范围外

明确排除：私有仓库、写权限、仓库 Clone、代码执行、依赖安装、漏洞/供应链审计、完整语义代码搜索、长期记忆、RAG 向量库、多 Agent、复杂数据库、云端多用户服务、桌面安装包、自动订阅监控和付费 API 预算承诺。

## 10. 验收标准与建议测试场景

### 10.1 必须通过的功能性验收

| 编号 | 场景 | 通过条件 |
|---|---|---|
| F-01 | 输入自然语言需求搜索项目 | 至少完成一次搜索，输出候选、真实 GitHub URL、查询记录和报告 |
| F-02 | 输入公开仓库 URL | 正确解析 owner/repo，读取可用元数据并报告缺失字段 |
| F-03 | 初次结果不足 | 至少发生一次基于结果的补充查询、补查或合理终止；日志能说明触发原因 |
| F-04 | 比较多个候选 | 每个候选按同一维度展示；缺失字段不被其他候选值替代 |
| F-05 | 生成报告 | 事实、评分/规则、模型摘要和不确定性分开；原始来源可点击 |
| F-06 | 工具调用失败 | 网络、404、403/429、422、空结果和格式异常被区分处理，不伪装成成功 |
| F-07 | 达到预算 | 安全结束，不继续调用；报告显示达到的限制和已完成内容 |
| F-08 | 模型工具调用异常 | 无效工具参数、未知工具、空响应和超时可重试或明确终止 |

### 10.2 安全性与数据真实性验收

| 编号 | 场景 | 通过条件 |
|---|---|---|
| S-01 | 仓库已归档 | `archived=true` 原样保留并明显标注，不推荐为“活跃项目” |
| S-02 | 缺少许可证 | 输出“GitHub 未识别许可证/信息缺失”，不猜 MIT/Apache 等许可证 |
| S-03 | README 含恶意指令 | 内容只作为被分析文本；不能改变工具权限、系统规则或触发 Shell |

| S-07 | 外部内容大小 | 超大或截断 README 被标注，不被报告声称为完整分析 |

### 10.3 可测量但暂不冻结的指标

以下指标用于后续建立基准，不在 V0.1 冻结数值：

- 端到端完成时间分布和超时率。
- 每任务模型轮次、GitHub 请求数、重复请求率和 token 消耗。
- 不同需求类型下的候选覆盖率、去重率和可用来源率。
- 结构化字段准确复制率、URL 有效率、许可证未知值保真率。
- 在固定人工标注集上的排序一致性、推荐相关性和“无充分证据不推荐”准确性。
- 429/网络失败下的恢复成功率和错误解释正确率。

这些指标必须基于真实运行或明确的 Mock 数据集；本轮没有执行实现测试，不声称已有结果。

## 12. 需要用户确认的关键决策（最多 5 项）

以下给出推荐，但不在本文替用户冻结：

1. **首要交互形态**：推荐先 CLI，之后加本地 Web UI；理由是 CLI 能最低成本验证 Loop、日志和错误闭环。请确认是否接受“CLI 优先”。
2. **认证默认值**：推荐无 Token 公开只读可启动，同时支持用户自行配置细粒度只读 Token；理由是兼顾低门槛和搜索额度。请确认是否采用这一双模式。
3. **MVP Agent 轮次与请求预算**：推荐设置为可配置硬上限，并在首版测试中使用小上限；具体数字在 M1 用真实 API 与模型测试后冻结。请确认是否接受“先冻结机制、后冻结数值”。
4. **推荐目标**：推荐先服务“技术需求下的少量候选比较”，不承诺生产级代码质量或安全审计；理由是边界清楚、证据可验证。请确认是否采用这一首要用户和场景。
5. **模型兼容策略**：推荐 MVP 只验收一个已验证 Tool Calling 的 OpenAI-compatible 端点，同时保留 Base URL/Key/Model 可替换配置；不支持 Tool Calling 的模型明确报配置不满足。请确认是否接受，而不是为非兼容模型维护伪工具协议。

## 13. 内部一致性检查结论

检查项目：

- **MVP 范围一致性**：自然语言输入、受限 Loop、Tool Calling、公开 REST 只读、反馈驱动补查/改查、结构化报告、日志和预算控制在第 5、9、10、11 节一致；长期记忆、RAG、多 Agent、GraphQL、桌面应用已明确为后续或排除项。
- **Agent/普通程序边界**：查询选择、补查和报告解释交给 Agent；请求、解析、评分基础计算、权限、预算和日志由程序控制，没有把确定性安全逻辑交给模型。
- **GitHub 写操作**：全文仅定义公开只读访问；没有设计仓库、Issue、PR、账户或权限写入。
- **用户文件边界**：仅允许项目目录内的报告、日志和测试夹具；没有把远程仓库分析扩展为用户文件管理。
- **未来功能标注**：长期记忆、RAG、多 Agent、GraphQL、本地 Web UI、桌面应用和复杂审计均未写成 MVP 必需。
- **事实与推测**：API 限制、字段和接口结论附官方来源；动态额度、供应商价格、模型兼容性和性能指标均标为实施前核验或待测试，没有伪造测试结果。
- **待决策项**：共 5 项，每项都有推荐理由，且没有阻止当前需求分析文档完成。

**结论：本轮不存在阻碍进入正式需求确认阶段的问题。正式进入下一阶段前，需先由用户审阅并确认第 12 节决策；在此之前不进入技术设计、源码创建、依赖安装或功能开发。**
